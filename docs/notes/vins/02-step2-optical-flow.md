# STEP2 · FAST 角点 + KLT 金字塔光流跟踪

## 这一步解决什么问题

后面 STEP4 要三角化、要 PnP，前提是**同一个物理点在多帧图像里都能找到**。所以这一步的任务只有一句话：建立跨帧的点对应关系，并且要稳。

单目没有第二个相机做外参约束，点的对应一旦跟断，后面全部几何都没有输入。这是整条流水线里最基础、也最容易悄悄坏掉的一环。

## 为什么用光流，不用描述子

ORB 那套「提特征 + 算描述子 + 暴力/FLANN 匹配」是为**大基线**（重定位、回环）设计的。VINS 前端跟踪的是**连续帧**，基线只有几厘米到几十厘米，像素位移小，这种情况光流明显更合适：

- 计算量小：在上一帧点位置上局部搜，比全图描述子匹配便宜一个数量级。
- 有亚像素精度：`calcOpticalFlowPyrLK` 输出 `Point2f`，是亚像素级。
- 天然稳定：连续帧亮度变化小，光流假设（亮度恒定、小位移）成立得比大基线匹配好。

VINS-Mono 官方的 `feature_tracker.cpp` 用的也是这套，不是 ORB。

## 怎么做的

1. **第一帧**：`goodFeaturesToTrack` 取 600 个角点，`qualityLevel = 0.01`，`minDistance = 10`。内部用的就是 Shi-Tomasi 角点响应（FAST 系的一种稳定变体）。
2. **逐帧向前跟踪**：`calcOpticalFlowPyrLK`，窗口 21×21，金字塔 3 层。
   - 3 层金字塔是为了应对帧间位移较大的情况：先在缩小 4 倍的图上估大致位移，再逐层精化。
3. **反向校验**：对跟踪到的点再反向跟踪回原帧，正反向位移差超过阈值的判定为误匹配剔除。这一步能砍掉大部分跟到纹理相似区域的错点。
4. 跟踪点数不足时补提新角点（保持数量稳定）。

关键约束：输入必须是单通道 8 位图（`CV_8UC1`）。EuRoC 的 PNG 是灰度图，读进来直接可用；如果读到三通道要先转灰度。

## 图怎么读

图上叠两类元素：上一帧的绿点 → 这一帧的绿点之间连线。判断标准有三条：

- **线方向是否一致**：相机整体平移时，所有光流矢量应该指向同一方向、长度相近。方向杂乱说明跟踪错乱，通常意味着参数（窗口、层数）不对或图像质量差。
- **绿点密度**：绿点应该密集分布在纹理丰富处（桌面、箱子、地面纹理），天空/白墙区域本来就提不出角点，稀疏是正常的。
- **红点数量**：红点是校验失败被剔除的。红点占比高说明帧间位移过大或图像模糊。

## 验收标准与实测值

| 指标 | 要求 | 实测 |
|---|---|---|
| 首帧角点数 | 数百 | 150 |
| 跟踪成功数 | — | 139 |
| 跟踪成功率 | > 90% | 92.7% |
| 平均位移 | 数像素级 | 数像素 |

92.7% 的成功率在连续帧上是正常水平。掉的那 7% 基本是位移到图像边界外、或者落在低纹理区域的点。

## 与 STEP4 的衔接

这一步的输出不是「每帧一张点表」，而是**每个特征 ID 在各帧的观测链**。STEP4 的滑窗需要的是「某个点在第 200、202、204、206、208、210 帧分别在哪」，而不是「第 204 帧有 300 个点」。

因此数据结构应该按特征存：

```
Feature {
    id
    obs[frame_idx] = { px (像素坐标，可视化用), nv (去畸变归一化坐标，几何计算用) }
    tracked_count
}
```

链路越长的特征越值钱：一个在 6 帧里都跟踪到的点，才能给出 6 个重投影约束。这也是 STEP4 里「526 个全链特征」这个数字的意义。

## 常见错误

- 忘了转灰度，光流输入 3 通道直接报错。
- 用 `status` 数组过滤时下标错位（`status` 是 `uchar` 的 `Mat` 或 vector，取值要按 `status[i]`）。
- 只做正向跟踪不做反向校验，误匹配进 STEP4 后会表现为「三角化出来的点深度乱跳」。
- 每帧重新提全部角点、不做跨帧 ID 继承，等于每帧都是新地图，后面完全串不起来。
