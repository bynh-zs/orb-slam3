# STEP7 · 主循环出轨迹

## 这一步解决什么问题

前六步都是在「某一个滑窗」上做工。STEP7 把它们串成一个真正的里程计：读第 k 帧 → 匹配特征 → 填滑窗 → 判初始化 → 优化 → 输出第 k 帧位姿 → 滑窗右移一格。

对应官方 `estimator.cpp::processImage`，加上 `estimator_node.cpp` 里那个「来一帧调一次」的循环。

## 主循环的每一帧要做什么

```
for 每一帧 k:
    1. 读图 + 取该帧时刻之前的 IMU 采样
    2. 光流跟踪上一帧特征；数量不足则补提
    3. 把新帧塞进滑窗
    4. 若尚未初始化:
         若滑窗已有足够视差 → 跑 STEP4 + STEP5
         否则 continue（继续攒帧）
    5. 已初始化: 用 STEP3 预积分 + STEP6 滑窗优化更新状态
    6. 输出第 k 帧位姿，滑窗右移（触发边缘化）
```

第 4 步那个 `continue` 是理解 VINS 的关键：**初始化不是一开始就完成的，而是在攒够视差的第一个时刻才发生的**。MH_01 起飞段慢，真实 VINS 往往要跑几十帧才初始化成功。这也是本仓库 STEP4 为什么选帧 200→210 这一对：那是这段数据里视差最大的一段。

## 轨迹输出与对齐比较

输出 `TUM` 格式的一行四位姿：

```
timestamp tx ty tz qx qy qz qw
```

与真值 `mav0/state_groundtruth_estimate0/data.csv` 比较时，必须先做两件事：

1. **时间对齐**：按时间戳插值到同一组时刻。
2. **Sim(3) 对齐**：单目/无绝对观测的 VINS 与真值之间差一个 7 自由度的相似变换（旋转 + 平移 + 尺度）。直接逐点算欧氏距离没有意义，要先用 Umeyama 求 Sim(3)，再算 ATE。

不做 Sim(3) 直接比，会得到「轨迹形状一模一样但误差 100 米」的结论 —— 那不是算法错，是比较方法错。

## 验收标准

| 指标 | 预期 |
|---|---|
| 轨迹形状 | 与真值同构：起飞段的直线、转向的弧线都对得上 |
| ATE (Sim3 对齐后) | 米级以内（MH_01 全长约 80m） |
| 尺度 s | 与 STEP5 解出的 s 一致，且不随时间漂 |
| 运行稳定性 | 全程不 crash、不 NaN |

可视化：俯视 xy 平面「估计轨迹 vs 真值轨迹」叠图 + 误差随时间曲线。

## 与官方实现的差别

本仓库是**单线程、离线、整段读文件**的实现。官方是 ROS 节点、订阅话题、多线程（前端跟踪与后端优化分线程）。差别带来两个后果：

- 官方有时间戳同步、队列丢帧处理；离线实现可以假设数据齐全，所以不必处理。
- 官方有回环检测与全局位姿图（`pose_graph`），本仓库不包含。回环属于后端，不属于「前端工程」范围。

这一点在评估「跑出来的轨迹为什么比官方差」时必须先说明：不是实现错，是少了回环和后端优化。

## 常见错误

- 直接把无尺度位姿当真值比，误判为「尺度错了」。
- 时间戳用图像帧时间（纳秒）与真值时间（纳秒）错位，插值插到空气里。
- 滑窗右移时忘了同步移除对应的特征观测，特征 ID 表越滚越大。
- 初始化成功后仍每帧重跑 STEP4，位姿被反复重置。
